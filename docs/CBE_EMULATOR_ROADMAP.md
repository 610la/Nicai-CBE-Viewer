# CBE Web Emulator Roadmap

## Goal

Build a generic browser-based emulator that can load any standard CBE game file from the Nicai/MStar-style corpus. `众神之战` is an anchor sample for reverse engineering because it has rich `.sce/.map/.actor/.xse` coverage, but the architecture must not become a one-game port.

## Strategy

Use two tracks in parallel:

1. **Corpus track:** keep the archive loader, resource decoders, viewer, and compatibility reports generic. Every tool should be able to run over a directory of `.CBE` files and report which format features each game uses.
2. **Engine truth track:** use one or two rich games as executable anchors to reverse the real runtime ABI and VM. Every recovered rule must become a generic decoder/runtime contract, not a hardcoded game script.

This is faster than building an empty emulator shell first, because the unknowns are in the binary VM and resource grammars. It is also safer than only reverse-engineering one game, because corpus reports catch assumptions that only work for `众神之战`.

## Architecture Boundary

- **Archive FS:** CBE section scanner, resource table, names, raw payload access, fixed payload access.
- **Asset codecs:** GIF palette fixup, image metadata, audio pass-through, text/string scans.
- **Resource parsers:** `.sce`, `.map`, `.actor`, `.xse`, plus unknown binary summaries.
- **Runtime services:** generic service-object ABI model for open/convert/read methods, not per-game file reads.
- **VM core:** XSE record tables, group dispatcher, operand resolution, writeback, timers, active/cursor state.
- **Renderer/input/audio shell:** browser canvas, input events, frame scheduling, audio hooks, save/load state.
- **Compatibility matrix:** per-game support status and blockers.

## Milestones

### M0: Generic Archive Browser

Load arbitrary standard CBE files, list resources, preview fixed images/audio/text, and report unsupported or malformed files without crashing.

### M1: Corpus Compatibility Matrix

Scan all CBE files in a corpus and report section counts, resource counts, extension mix, scene/script presence, image fixups, and loader failures.

### M2: Scene Evidence Runtime

For games with `.sce/.map/.actor/.xse`, decode scene/resource links and show a clearly labeled evidence view. This must not claim to be gameplay.

### M3: Trace-Only VM

Run XSE group dispatch and cursor state with no visible effects until operand resolution and writeback are proven. `众神之战` currently sits here.

### M4: Effect VM

Enable script effects only after writeback targets, timers, branches, and object/value semantics are resolved through generic helpers.

### M5: Playable Web Shell

Drive renderer/input/audio from the generic VM and resource parsers. Add save-state snapshots and per-game compatibility flags.

## Decision Rules

- Prefer a real binary/runtime rule over a visual guess.
- Do not make a game-specific shortcut unless it is isolated as a temporary probe.
- A decoded scene preview is evidence, not emulation, until the VM writes the state that produced it.
- Screen-transition footage, such as grid/shutter wipes during loading, belongs to the compositor/scene-change track and must not be mistaken for terrain map decoding.
- When a heuristic works on one game, run it against the corpus matrix before promoting it to core.
- Keep `众神之战` as the richest anchor, then cross-check with at least one menu/action game and one arcade game.
